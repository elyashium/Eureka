# Platformer game production craft

## Engine choice for a browser-first 2D platformer

### Takeaway
For a 2D action-platformer whose first release is a web game, Phaser 4 with TypeScript is a direct fit: it is a browser-focused 2D framework, has cameras, input, animation, tilemaps, sound and arcade physics, and can be wrapped later for desktop and mobile. Godot is the better alternative when an editor-centered workflow and native desktop/mobile exports are as important as browser delivery; Unity is viable too, but assess its Web target constraints and loading/runtime costs before choosing it for a small 2D browser game.

### Cited Findings
- Phaser 4 is an open-source 2D HTML5 framework using JavaScript or TypeScript and rendering with WebGL or Canvas on desktop and mobile browsers. Its own docs say it can also be packaged for iOS, Android, Steam and native apps using third-party tools. [Phaser 4 documentation](https://www.phaser.io/oss/docs)
- Phaser Arcade Physics is a lightweight physics system with rectangle and circle shapes. Its documentation explicitly lists platformers among its intended use cases; choose it for a side-scroller with simple player, enemy, projectile and pickup shapes. Arcade and Matter are separate physics systems and their bodies do not collide with each other. [Phaser Arcade Physics](https://docs.phaser.io/phaser/concepts/physics/arcade)
- Godot 4 web exports require WebAssembly and WebGL 2.0 and use the Compatibility renderer. The stable guide says Godot 4 C# projects cannot currently export to Web. Single-threaded export is the default/preferred option because threaded export requires cross-origin isolation headers; web audio also has documented limitations, including unsupported AudioEffects in the default Sample playback mode. Native Android/iOS builds can perform significantly better than the web export. [Godot: Exporting for the Web](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)
- Godot's `CharacterBody2D` offers manual character movement and collision handling. `move_and_slide()` is intended for platformers; the engine guide demonstrates gravity, jump velocity, an `is_on_floor()` check and `move_and_slide()` inside the physics callback. [Godot: Using CharacterBody2D](https://docs.godotengine.org/en/stable/tutorials/physics/using_character_body_2d.html)
- Unity 6's Web platform supports current desktop Chrome, Firefox, Safari and Edge when WebGL 2, HTML5 and WebAssembly requirements are met. Its current compatibility documentation also lists iOS Safari 15+ and Android Chrome 58+ as supported mobile browser targets. Web builds have browser-specific restrictions and network access uses browser mechanisms; direct TCP/UDP sockets are unavailable. [Unity 6 Web browser compatibility](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/webgl/intro/browsercompatibility), [Unity 6 Web networking](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/webgl/develop/networking)
- Capacitor can add a native iOS/Android runtime to a modern JavaScript project, while exposing native APIs through plugins when needed. Electron packages HTML, CSS and JavaScript into cross-platform Windows, macOS and Linux desktop applications by embedding Chromium and Node.js. [Capacitor documentation](https://capacitorjs.com/docs), [Electron documentation](https://www.electronjs.org/docs/latest/tutorial/tutorial-prerequisites)

### Inferences
- Start with Phaser 4 + TypeScript + Vite if browser playability and multiplayer integration are the first milestones. Use the native browser build as the source of truth; add a Capacitor shell for mobile apps and Electron or another desktop wrapper only after the browser version is stable. The toolchain stays close to the technologies used for the website, but wrappers still require platform-specific input, screen-size, audio, packaging and store work.
- Pick Godot instead if an editor for scenes, animation and level assembly is central to the team, or if native PC/mobile builds are the main product and browser is one export. Prototype the web export early because threading headers, audio features, C# support and payload size can affect hosting and performance.
- Use Unity mainly when the team already knows it, needs its wider production ecosystem, or expects to share substantial Unity technology with another project. For a modest 2D web platformer, Phaser or Godot is likely a simpler starting path; that is a project-fit recommendation, not a claim that Unity cannot build the game.
- Do not choose a physics engine because it promises realistic simulation. For this style of platformer, stable collision and tunable movement matter more than physical realism. A custom character controller can sit on top of a simple collision system when built-in movement does not give the desired feel.

### Gaps
- No engine can be called definitively best without knowing team experience, intended concurrent player count, browser game portal requirements, and whether PC/mobile are web wrappers or native builds. Revisit that decision after a playable movement prototype and target-device tests.

## Movement, collisions, interaction, camera, enemies and bosses

### Takeaway
The game loop reads an abstract action set, updates a player movement model, resolves collisions, advances game states, then renders animation and camera effects. Keep the art sprite separate from its collision body, and make a short greybox level the first test bed. Build enemies and bosses as explicit state machines whose hitboxes and vulnerability windows turn predictable animation into readable gameplay.

### Cited Findings
- In Phaser Arcade Physics, a body has velocity, acceleration, drag, gravity, maximum speed and floor/wall contact flags; the Phaser docs show how to use `onFloor()` and the `blocked` direction state. Static bodies do not move and are suitable for ground/platforms. Physics debug graphics can show bodies and velocity vectors. [Phaser Arcade Physics](https://docs.phaser.io/phaser/concepts/physics/arcade)
- Godot's documented starter controller adds gravity, sets vertical jump speed only when jump is pressed and the body is on the floor, applies horizontal input, and calls `move_and_slide()`. The guide says the sample is only a starting point before adding features such as acceleration, double-jump and coyote time. [Godot: Using CharacterBody2D](https://docs.godotengine.org/en/stable/tutorials/physics/using_character_body_2d.html)
- Phaser colliders can either separate solid bodies or only detect overlap, and callbacks can run when a collision/overlap occurs. The engine's factory supports a `processCallback` to filter interactions before they are processed. [Phaser Arcade collider API](https://docs.phaser.io/api-documentation/class/physics-arcade-collider), [Phaser Arcade physics guide](https://docs.phaser.io/phaser/concepts/physics/arcade)
- Phaser camera follow can use horizontal/vertical interpolation and a deadzone; integer pixel rounding and integer zoom can reduce pixel-art jitter. [Phaser cameras guide](https://docs.phaser.io/phaser/concepts/cameras), [Phaser Camera API](https://docs.phaser.io/api-documentation/class/cameras-scene2d-camera)
- Tiled object layers support freely positioned and resized points, rectangles, polygons and polylines with per-object custom properties. The Tiled docs suggest objects for data that would otherwise be hard-coded (such as spawn points), and custom properties can represent object types and values. [Tiled layers](https://doc.mapeditor.org/en/stable/manual/layers/), [Tiled custom properties](https://doc.mapeditor.org/en/stable/manual/custom-properties/), [Tiled JSON map format](https://doc.mapeditor.org/en/latest/reference/json-map-format/)
- Tiled object references can connect two map objects, such as a switch and a door, or an NPC and a path. This allows level-authored links rather than hard-coding every relationship. [Tiled object connections](https://doc.mapeditor.org/en/latest/manual/objects/)
- Phaser combines mouse and touch into a pointer input API for interactive game objects; its keyboard API supports polling or events. [Phaser input guide](https://www.phaser.io/oss/docs/phaser/concepts/input), [Phaser keyboard key API](https://docs.phaser.io/api-documentation/class/input-keyboard-key)
- Game Programming Patterns describes state machines as a way to give an object different behavior in distinct states, useful for making behavior explicit rather than burying transitions in conditionals. [Game Programming Patterns: State](https://gameprogrammingpatterns.com/state.html)

### Inferences
- Use named actions such as `left`, `right`, `jump`, `attack`, `interact`, `pause`; map keyboard, gamepad, and touch controls onto those same actions so the gameplay code is device-independent. On phones, place large, reachable jump/attack controls over the game viewport and let players reposition or hide them if the design permits.
- Tune running and jumping through a small set of measured values: horizontal acceleration, maximum run speed, ground braking/drag, air control, gravity, jump impulse, terminal fall speed and jump-release behavior. Start with a jump that is triggered on the floor. Add a short coyote-time timer after leaving a ledge and a jump-buffer timer that remembers a press made just before landing. These two windows make inputs more forgiving; they should be adjustable values rather than scattered frame-count checks.
- Separate the animated sprite from a simple stable body (rectangle/capsule) so the character art can stretch, lean, flip and change pose without changing where the feet collide. Add small temporary attack boxes for sword/hand attacks, an enemy hurtbox, and a ground sensor if the main body alone produces unreliable floor checks. Use a solid collision for walls and platforms, and overlap-only triggers for coins, checkpoints, damage zones and pickups.
- Drive animation from game state and velocity: idle, run, rise, fall, land, attack, hurt and death are a useful initial set. Physics chooses movement and collision; animation illustrates it. Avoid using animation frames as the source of truth for where the body is. Phaser supports frame-based sprite-sheet/atlas animation and completion events for finite animations, which can coordinate one-shot events such as a swing or landing. [Phaser animations](https://docs.phaser.io/phaser/concepts/animations), [Phaser animation events](https://docs.phaser.io/api-documentation/event/animations-events)
- Use Tiled for visual tile layers plus an object layer containing spawn points, patrol limits, interactables, checkpoints, boss arena triggers and camera zones. Give objects a small vocabulary of properties (`kind`, `id`, `targetId`, `range`, `checkpoint`, `enemyType`); have the game read the map and instantiate reusable components from those properties. Keep a separate collision layer or tile property from decorative art, so bushes and painted ledges are not accidentally solid.
- A simple interaction flow is: find the closest interactable within range and in front of the player; show its prompt; on the `interact` action, call the object's behavior. A switch can update a linked door's state; a checkpoint saves a respawn location; a collectible increments persistent progress. This pattern keeps control input separate from object behavior.
- Use an enemy state machine like `patrol → detect → pursue → windup → attack → recover → patrol`. A boss can add `guarded`, `stunned`, `phase transition` and `defeated`. Each attack should have a tell/windup, a short active hitbox window and a recovery window where the boss is punishable. Telegraph attacks with pose, particles and sound; give the player a dodge/jump/spacing answer; use phase thresholds to change attack selection rather than writing one giant update function. These boss pacing recommendations are design guidance inferred from state-machine structure, not documented claims about Fancy Pants' original source code.
- Implement one basic enemy, one checkpoint, one collectible, one door/switch and one simple boss in the greybox before making many levels. Tune jump distances and attack range against the actual map geometry. Add art and effects once collision and input feel consistent.
- Keep a fixed conceptual order in each simulation tick: capture input, update timers/states, apply velocity/gravity, move and resolve collision, handle overlaps/damage, select animation, then render. The engine handles some or all ordering, but thinking in this order helps prevent animation or interaction events from running against stale physics state.
- For parallax and screen composition, place background, midground, gameplay and foreground on separate layers; use a camera deadzone so the player has room to run before the view scrolls. Test a camera at normal, narrow and phone aspect ratios; reserve screen-space UI rather than placing every prompt in the world.

### Gaps
- Exact acceleration, gravity, frame counts, coyote-time length and boss timings are feel decisions and vary by character scale, player skill and art style; there is no universal “Fancy Pants” setting. Tune through play, not guessed constants.
- The source code or original design documents for Fancy Pants' proprietary collision and boss systems were not available in this research slice. The implementation patterns above are general modern recommendations, not claims about how that game was coded.

## Sprite art, animation, music and sound

### Takeaway
Treat character animation, collision, level tiles and audio as separate production assets with repeatable export conventions. Keep editable source files, export transparent image atlases plus frame metadata, and test them in the running game early. For sound, support browser codec variation and wait for a player gesture before starting audio; keep licenses and attribution records with every asset.

### Cited Findings
- Aseprite's docs describe a sprite sheet as a single image holding animation frames. Sprite sheets can be exported from visible layers or selected animation tags, with JSON metadata; the CLI can export one or several animations and pack a texture atlas. The docs recommend retaining `.aseprite` source files to preserve frames and layers. [Aseprite sprite sheets](https://aseprite.org/docs/sprite-sheet/), [Aseprite CLI export](https://aseprite.org/docs/cli/), [Aseprite save format](https://aseprite.org/docs/save)
- Phaser uses frame-based animations from sprite sheets or texture atlases; an animation is a sequence of frames played at a given rate, and a sprite can use overlapping frames in different animations. The animation-complete event fires for finite animations, making it useful for one-shot sequences; infinite loops never complete. [Phaser animations](https://docs.phaser.io/phaser/concepts/animations), [Phaser animation events](https://docs.phaser.io/api-documentation/4.0.0/event/animations-events)
- MDN lists MP3, AAC, Opus, Vorbis and FLAC among common codecs and explains that containers and browser codec support differ. Phaser's sound manager selects Web Audio when available and falls back to an HTML audio tag; its docs say browser audio usually remains locked until click/tap and recommend supporting at least MP3 for publishing. Phaser also supports marked sections and audio sprites. [MDN audio codecs](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Audio_codecs), [Phaser audio guide](https://docs.phaser.io/phaser/concepts/audio)
- MDN explains that browsers usually block audible autoplay until there is a user interaction; creating or resuming `AudioContext` in a click/tap handler is the standard unlock path. It also recommends user controls for sound. [MDN Web Audio best practices](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices), [MDN autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- Creative Commons licenses differ: BY requires attribution; NC prohibits commercial use; ND restricts sharing adaptations; SA requires adaptations to use the same license. CC recommends that reusers check the specific license terms before using an asset. [Creative Commons FAQ](https://creativecommons.org/faq/), [Creative Commons license chooser](https://creativecommons.org/chooser/)
- Audacity exports a rendered mix as an audio file while preserving the editable project separately. Its current support docs note that Opus/M4A can offer higher quality than MP3 at a similar size, while lossless formats are useful for source/archival audio. [Audacity export guidance](https://www.audacityteam.org/manual/getting-started/export-your-audio/), [Audacity project and export guide](https://support.audacityteam.org/basics/saving-and-exporting-projects)

### Inferences
- For hand-drawn non-pixel art, draw key poses at a stable canvas size in a raster/vector art tool, then export clean transparent frames or an atlas. For pixel art, Aseprite's layers, tags, onion skinning and sprite-sheet export are a compact, purpose-built pipeline. Keep a working source file plus exported PNG/atlas JSON; name frames and tags consistently (`player_run`, `player_jump`, `boss_slam`) so programmers can map them to states.
- Draw the player in profile with a readable silhouette, consistent feet anchor and enough distinct poses to make horizontal direction, rising/falling, landing and attacks clear at play size. Start with idle/run/jump/fall/attack/hurt; add decorative loops after controls feel good. For frame animation, a smaller number of clean poses can read well when timing and spacing are strong; bone animation is an option for characters with many costume/weapon variations, but may take extra setup to get expressive squash, stretch and hand-drawn energy.
- A practical art export contract lists: logical canvas dimensions, pivot/feet anchor, frame/tag names, transparent background, whether frames are trimmed, atlas padding, and texture filter. Pixel art usually uses nearest-neighbor filtering and integer camera scaling to retain crisp edges; smooth hand-drawn art may need linear filtering. Always inspect at final viewport resolution and device scale.
- Use a drawing tablet/scan-and-clean workflow if the target is a loose, pencil-like style. Aseprite is pixel-centric, so it is not automatically the best tool for a hand-drawn style. Inspiration from Fancy Pants should be expressed through original characters, shapes, settings, music and level layouts rather than copying the recognizable character design or assets.
- Compose music as loopable per-area tracks and create short, separately triggerable effects for footsteps, landings, attacks, pickups, damage, switches and boss cues. Keep muted/volume controls. Create or commission originals when possible; save the source session (e.g., DAW project), stems if needed, final compressed exports, and the license/permission record. The editable project matters for future mix and timing edits; the game only needs the rendered final files.
- For a browser prototype, offer MP3 plus a second tested format only if device/browser testing shows value; for short effects consider an audio sprite so the browser downloads fewer independent assets. Decode/unlock sound on the first “Play” or “Start” click/tap, and start background music only after that gesture.
- Maintain an asset register with filename, author/creator, source URL, license name/version, date acquired, allowed platforms/commercial-use status, attribution text, modifications, and proof of purchase or permission. Avoid NC assets for a commercial release; do not assume “free download” means game redistribution rights. Review SA/ND conditions when embedding or adapting assets, and get legal advice if a planned use is unclear.

### Gaps
- Fancy Pants' original project files, complete animation sheets, composer contract and precise music/audio pipeline are not public in the sources covered here. Do not present an inferred asset tool, codec, frame rate or audio license as historical fact.
- The right audio bit rate, compression and atlas layout depend on final sound, browser targets, CDN costs and memory budget; compare on actual devices. Codec support is browser/version dependent, as MDN notes.
