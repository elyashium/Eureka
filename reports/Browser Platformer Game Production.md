# Build A Browser Platformer From Scratch

A browser platformer like *Fancy Pants Adventures* was made possible by a tight loop between drawing, animation, code, and instant playtesting: Flash let a small creator sketch a character, animate it, write its movement, and publish a playable SWF to the web. The lesson to carry forward is that the character’s movement and animation are the game’s foundation; levels, bosses, music, and multiplayer should grow around a fun controller. For a new browser-first project, use Phaser 4 with TypeScript for the client and a separate, authoritative TypeScript server such as Colyseus for small multiplayer rooms, with the movement rules shared between them. Start with a fixed-step, kinematic platform controller, a greybox level, and two-player co-op before investing in a large world or account system. Keep original art and sound sources, export tested atlases and audio, and build through browser, then PC and mobile packaging. Fancy Pants’ exact original physics, ActionScript version, and audio pipeline are not publicly documented, so this guide separates known history from recommended modern practice.

## Flash made animation and code travel together

### What the Flash workflow looked like

Flash Professional centered production around a Stage, a layered Timeline of frames and keyframes, a Library of imported and authored assets, and ActionScript for behavior. Artists could draw directly in the authoring tool or import raster artwork; frame-by-frame animation and tweens lived alongside code and sound. The resulting project could be published as a SWF file that Flash Player ran in the browser. Adobe’s CS6 reference documents those tools and sound options, while Brad Borne later described Flash’s practical advantage: he could draw, run the game, inspect an animation, and adjust it in the same environment. ([Adobe Flash Professional CS6 reference](https://help.adobe.com/archive/en/flash/cs6/flash_reference.pdf); [Borne Games FAQ](https://www.bornegames.com/faqs/))

That workflow made a web game easy to circulate as a small playable artifact, but it depended on a browser plugin that is now retired. Adobe ended Flash Player support after December 31, 2020, and blocked Flash content in the player beginning January 12, 2021. A modern project should reproduce Flash’s quick feedback loop with a browser development server and fast reloads, not reproduce its plugin delivery model. ([Adobe Flash Player end-of-life notice](https://www.adobe.com/support/flashplayer/downloads))

### What is documented about Fancy Pants

Brad Borne says the idea began as a stick-figure animation, followed by code and then ground; he focused on making the character feel good moving back and forth. His official history connects the drawn character to notebook sketches, flipbooks, and frame-by-frame Flash animation. The original World 1 page describes momentum-based platforming, sketch-like levels, ramps, loops, and platforms. Public records place the browser release in 2006. These sources support an iterative, movement-first origin story, but they do not reveal the original project files or source code. ([Borne Games: About](https://www.bornegames.com/about-me/); [Kongregate Developers interview with Brad Borne](https://kongregatedev.ghost.io/a-fast-and-fancy-dev-qa-with-brad-borne/); [Borne Games: original World 1](https://www.bornegames.com/games/fpa-world-1/original/); [MobyGames: World 1 credits](https://www.mobygames.com/game/35321/the-fancy-pants-adventure-world-1/credits/browser/))

The original controls were simple enough to learn quickly—left and right to move, down to duck or slide, and up to enter doors—but the terrain rewarded momentum. Later versions added more moves and actions; the World 1 Remix documentation, for example, describes sliding, rolling, and a landing boost. Borne has said movement, animation, physics, and ground shape were tuned together, which made ports harder than simply transferring the artwork. His retrospective is a strong design lesson: a platformer’s feel comes from the relationship between input, acceleration, animation, collision, and the shape of its routes. ([Borne Games: original World 1](https://www.bornegames.com/games/fpa-world-1/original/); [Borne Games: World 1 Remix](https://www.bornegames.com/games/fpa-world-1/remix/); [Kongregate Developers interview](https://kongregatedev.ghost.io/a-fast-and-fancy-dev-qa-with-brad-borne/))

Borne later described rebuilding the game in ActionScript 3, but that does **not** establish which ActionScript version powered the first release. A 2007 development post reported a 72-frame idle animation at 30 frames per second for World 1, and later described 514 frames of idle behavior for World 2—evidence of the attention he gave the character, not a requirement that every modern sprite needs hundreds of frames. Public sources do not establish the first game’s exact physics equations, collision shapes, FLA structure, sound formats, music license, or animation export process. The credits database names music and sound contributors, but it is not a production postmortem. ([Borne Games: Christmas ’13 update](https://www.bornegames.com/2013/12/christmas-13-update/); [Borne Games: Frames](https://www.bornegames.com/page/19/); [MobyGames: World 1 credits](https://www.mobygames.com/game/35321/the-fancy-pants-adventure-world-1/credits/browser/))

## Movement feel comes before content

### Build a character controller as a tuned instrument

A platform controller is usually easier to tune as a kinematic character than as a physically realistic body. The controller chooses horizontal speed, applies gravity, requests jumps, and resolves the character against platforms and walls. The art sprite should be separate from a stable collision body so the drawing can lean, stretch, flip, or change poses without making the player’s feet sink into the floor. Phaser Arcade Physics provides velocity, acceleration, drag, gravity, speed limits, floor and wall flags, static platforms, overlap callbacks, and debug drawing; Godot’s `CharacterBody2D` provides a similar manual-movement model through `move_and_slide()`. ([Phaser Arcade Physics](https://docs.phaser.io/phaser/concepts/physics/arcade); [Godot: Using CharacterBody2D](https://docs.godotengine.org/en/stable/tutorials/physics/using_character_body_2d.html))

Tune a small set of variables rather than scattering magic numbers: horizontal acceleration, maximum speed, ground braking, air control, gravity, jump impulse, maximum fall speed, and jump-release behavior. A short jump buffer remembers a jump pressed just before landing; coyote time permits a jump for a brief instant after leaving a ledge. These forgiveness windows make the game respond more like the player intended. As a useful starting relationship, for upward jump speed `v` and gravity `g`, the idealized jump height is approximately `v² / (2g)` and time to the apex is approximately `v / g`. Actual collisions, variable-height jumps, and air control change the result, so tune while playing a greybox level rather than chasing a universal formula.

The same collision categories can support most early gameplay. Solid platforms and walls stop movement; overlap-only triggers collect coins, activate checkpoints, open doors, detect hazards, and start boss encounters. A jump uses a floor-contact test; a punch or stomp can use a temporary attack box that is active only during the relevant move. An interaction action can find the nearest object in range and in front of the player, display a prompt, then ask that object to respond. Tiled object layers and custom properties can author spawn points, patrol bounds, switches, linked doors, checkpoints, and arena triggers as level data rather than hard-coded coordinates. ([Phaser Arcade collider API](https://docs.phaser.io/api-documentation/class/physics-arcade-collider); [Tiled layers](https://doc.mapeditor.org/en/stable/manual/layers/); [Tiled custom properties](https://doc.mapeditor.org/en/stable/manual/custom-properties/); [Tiled object connections](https://doc.mapeditor.org/en/latest/manual/objects/))

### Animation should explain the physics

Drive animation from movement state and velocity: idle, run, rising, falling, landing, attack, hurt, and death are enough to begin. The controller decides where the player is and whether the character is grounded; animation communicates what that motion feels like. Keep a consistent foot anchor and use clear silhouettes. Aseprite can export sprite sheets or atlases with JSON frame metadata and animation tags; Phaser plays frame sequences at chosen rates and emits completion events for one-shot animations. Keep editable source files as well as exported assets, and define the export contract up front: canvas size, anchor, frame names, trim behavior, atlas padding, and filtering. ([Aseprite sprite-sheet export](https://aseprite.org/docs/sprite-sheet/); [Aseprite CLI export](https://aseprite.org/docs/cli/); [Phaser animations](https://docs.phaser.io/phaser/concepts/animations))

Fancy Pants is hand-drawn and expressive, so inspiration should mean readable motion, playful momentum, and distinctive level routes—not copying its character, art, music, or recognizable assets. For a loose pencil style, use an illustration or raster-animation workflow that suits the artist; Aseprite is useful for pixel art but is not automatically the right tool for hand-drawn linework. For pixel art, nearest-neighbor sampling and integer camera scaling help avoid blur and jitter. For either style, inspect the character at the actual game viewport size, not just enlarged in the art editor.

### Treat sound as a designed and licensed asset pipeline

Compose or commission loopable area music and short effects that communicate footfalls, landings, attacks, pickups, switches, damage, and boss cues. Keep the editable music session and any needed stems; export compressed game files separately. Browsers normally require a player gesture before audible playback, so unlock or resume audio from the Play button and provide volume and mute controls. Phaser can use Web Audio or fall back to an HTML audio element; codec/container support varies, so verify the final files in target browsers and devices. ([Phaser audio guide](https://docs.phaser.io/phaser/concepts/audio); [MDN Web Audio best practices](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices); [MDN audio codecs](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Audio_codecs))

Keep an asset register that records each file’s creator, source, license and version, attribution text, commercial-use rights, modifications, and proof of purchase or permission. Creative Commons terms differ: for example, BY requires attribution, NC restricts commercial use, ND restricts adaptations, and SA can require adaptations to retain the same license. “Free to download” does not mean “licensed for a commercial game.” ([Creative Commons FAQ](https://creativecommons.org/faq/); [Creative Commons license chooser](https://creativecommons.org/chooser/))

## A browser-first engine should support fast iteration

### Choose for the first release and the team

For the stated goal—2D, browser first, multiplayer, and a possible PC/mobile path—the most direct fit is **Phaser 4 + TypeScript for the game client, Colyseus + TypeScript/Node.js for room servers, and a small shared simulation module**. Phaser supplies browser-oriented scenes, rendering, cameras, input, animations, tilemaps, sound, and simple platformer physics. Colyseus supplies isolated rooms and state synchronization. This recommendation assumes a small co-op or party room, not an MMO or competitive fighting game. ([Phaser 4 documentation](https://www.phaser.io/oss/docs); [Colyseus getting started](https://docs.colyseus.io/getting-started))

| Option | Best fit | Main trade-off |
|---|---|---|
| Phaser + TypeScript | Browser-first 2D client with quick web iteration | Native PC/mobile releases need third-party packaging or further platform work |
| Godot | Editor-centered scenes, animation, and native PC/mobile builds | Web uses WebAssembly/WebGL 2 Compatibility; Godot 4 C# projects cannot currently export to Web |
| PixiJS + custom systems | A team that wants to assemble its own lightweight engine | PixiJS is primarily a renderer; physics, scene workflow, tilemaps, and many game systems become team responsibilities |
| Unity | A team already experienced in Unity or committed to its wider ecosystem | Web has browser-specific limitations, including no managed C# threads and no raw IP socket access |

These trade-offs come from current official engine documentation. Godot is a serious alternative when an integrated editor and native targets outweigh simplest web deployment; Unity is viable where team expertise justifies it. Decide after a tiny export prototype, not from feature lists alone. ([Godot Web export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); [Godot platform FAQ](https://docs.godotengine.org/en/stable/about/faq.html); [PixiJS FAQ](https://pixijs.com/faq); [Unity Web limitations](https://docs.unity3d.com/6000.3/Documentation/Manual/webgl-technical-overview.html))

A workable source tree keeps client rendering separate from simulation and server code: `client/` owns Phaser scenes, input mapping, camera, UI, effects, and audio; `shared/` owns action types, movement constants, collision rules, and state transitions; `server/` owns rooms, authoritative player/world state, matchmaking, validation, and persistence. `assets/` holds editable sources and exported game assets; maps can be authored in Tiled and imported as data. That separation matters because the server should run the same movement rules without rendering or needing a browser window.

### Make one small level prove the whole game

Build a greybox with a start area, flat run-up, short and long jumps, a ramp or moving platform if desired, a switch-door pair, one checkpoint, one hazard, one basic enemy, and one boss arena. Give the camera a deadzone so the character has room to move before the viewport scrolls; test wide desktop and narrow phone aspect ratios. Phaser’s camera supports follow interpolation and deadzones. Use debug drawings for body bounds, floor sensors, interaction ranges, attack boxes, and spawn points; the debug view often reveals why a jump feels wrong faster than more artwork will. ([Phaser cameras](https://docs.phaser.io/phaser/concepts/cameras); [Phaser Arcade Physics](https://docs.phaser.io/phaser/concepts/physics/arcade))

Build enemies and bosses as explicit state machines, not one large pile of conditional code. A basic enemy can move from `patrol` to `detect`, `pursue`, `windup`, `attack`, and `recover`; a boss can add `guarded`, `stunned`, phase transitions, and `defeated`. Each attack needs a readable tell, a brief active hitbox, and a recovery window that gives the player a response and opportunity. For example, one boss might sweep a low attack that the player jumps over, then expose a weak point during recovery; another might leap toward the player and be vulnerable after landing. Reuse the movement language taught by the level so the fight tests what the player has learned.

Fancy Pants’ original Angry Penguin fight is described in a fan-maintained wiki as a charge into a wall followed by an opening to attack; that account is secondary and should be treated as a design reference rather than evidence of its original source code or authorial intent. The general recommendation—to make a boss readable through telegraphed patterns and player-earned openings—is game-design guidance, not a claim about how Borne implemented the encounter. ([Fancy Pants Adventure Wiki: Angry Penguin](https://fancypantsadventure.fandom.com/wiki/Angry_Penguin))

## Multiplayer needs server truth and client responsiveness

### Let the server decide outcomes

Use a server-authoritative model: clients send inputs such as direction, jump, attack, and interact; the server owns accepted positions, collisions, pickups, damage, checkpoints, boss state, and rewards. A room holds the state for one match and sends initial state plus updates. Start with WebSockets over TLS (`wss://`) for room messages and keep packets small. Browser WebSocket is broadly available, but it has no built-in backpressure mechanism, so the client and server should bound queues, coalesce stale movement input, and limit message sizes and rates. ([Colyseus rooms](https://docs.colyseus.io/room); [Colyseus state synchronization](https://docs.colyseus.io/state); [MDN WebSocket API](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API))

To keep a local jump responsive, predict the player immediately on the client using the shared movement function. The client sends numbered input frames. The server advances the room at a fixed step, checks the inputs, and acknowledges the latest processed frame. The client then resets to the latest authoritative snapshot and replays its newer unacknowledged inputs. Remote players and bosses can be drawn from recent snapshots and interpolated. Colyseus documents this server-authoritative prediction, reconciliation, and interpolation model; its server-input guide includes a 30 Hz input step with physics substeps at 60 Hz as an example, not a universal setting. ([Colyseus netcode](https://docs.colyseus.io/netcode); [Colyseus client prediction](https://docs.colyseus.io/netcode/client-prediction); [fixed-timestep guide](https://docs.colyseus.io/netcode/server-input))

Keep network ownership concrete. The server can reject a jump when a player is not grounded, an attack outside its cooldown, a pickup outside reach, or damage during a boss’s guarded state. The client may play a quick visual effect optimistically, but durable health, inventory, score, checkpoints, and match results must come from server-confirmed state. For a first co-op game, local prediction plus remote interpolation is usually a simpler fit than full peer-to-peer rollback; add lag compensation only if testing shows that hit registration against moving targets feels unfair. These are architecture recommendations based on the documented networking primitives, not measured outcomes for this exact game.

### Plan for disconnects, browser pauses, and persistence

Browsers throttle animation callbacks in hidden tabs, and mobile apps can be suspended. Treat hiding or backgrounding as a pause/disconnect event, stop advancing client simulation on uncontrolled wall-clock time, and let the room decide whether to wait, reconnect, pause, or remove the player. Colyseus exposes authentication and room lifecycle hooks for joins, disconnects, reconnection, and disposal. Match rooms are ephemeral by default, so save persistent player progression or match results to a database at checkpoints, match end, or controlled room disposal—not on every rendered frame. ([MDN `requestAnimationFrame`](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame); [Colyseus room lifecycle](https://docs.colyseus.io/room/lifecycle); [Colyseus persistence FAQ](https://docs.colyseus.io/faq))

For a small prototype, guest identity and private room codes can avoid account work, while the server still validates join tokens, message size, rate limits, and every reward-affecting action. Check WebSocket origins as a browser security measure, but do not treat the Origin header as authentication. Deploy the game bundle as static files over HTTPS/CDN and run room servers separately behind a reverse proxy. Add Redis-based presence/room drivers and multiple server processes only when load tests show one process is insufficient. ([Colyseus authentication](https://docs.colyseus.io/auth/room); [MDN WebSocket server guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API/Writing_WebSocket_servers); [Colyseus deployment](https://docs.colyseus.io/deployment); [Colyseus scalability](https://docs.colyseus.io/scalability))

## Expand from browser to PC and mobile in stages

A disciplined sequence keeps the project small enough to learn from. First, make a one-level, single-player movement lab with keyboard and gamepad actions; tune movement, collisions, camera, and jump feel using placeholder shapes. Next, build a vertical slice containing one complete level loop, one collectible, a checkpoint, an interaction pair, a basic enemy, a boss, and a short audio/art pipeline. Then add a two-player room and verify connection, prediction, correction, disconnection, and rejoin on imperfect networks before expanding level count. These phases are a recommended plan, not a documented formula from any one engine maker.

Once the browser slice works on desktop and mobile browsers, measure real devices before committing to wrappers. Phaser games can be packaged for iOS and Android through tools such as Capacitor, but the Capacitor build still needs native project configuration and platform work. Test touch reach, safe areas, viewport changes, audio unlock/resume, memory and frame pacing, app suspend/reopen, and reconnect after network changes. Electron can package JavaScript, HTML, and CSS into desktop apps for Windows, macOS, and Linux. ([Phaser + Capacitor tutorial](https://phaser.io/tutorials/bring-your-phaser-game-to-ios-and-android-with-capacitor); [Capacitor documentation](https://capacitorjs.com/docs); [Electron documentation](https://www.electronjs.org/docs/latest))

If mobile WebView performance or native integration becomes a problem, Godot offers native exports for desktop, Android, and iOS as well as a Web export, but it uses a different implementation path and its web renderer/audio constraints need early testing. Keeping the multiplayer protocol, level data, asset conventions, and game rules cleanly separated makes a later native client or rewrite less expensive. For any engine, test target devices and supported browsers early: browser suspension, audio policies, rendering backends, input modes, and store requirements differ. ([Godot platform FAQ](https://docs.godotengine.org/en/stable/about/faq.html); [Godot Web export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html); [Capacitor iOS documentation](https://capacitorjs.com/docs/ios))

## Conclusion

The strongest lesson from Flash-era platformers is production coherence: art, movement, collision, animation, levels, and audio must be tuned as one experience, even when they are built by different tools and people. For this project, prove that coherence with one satisfying movement controller and a two-player room before building a large campaign. Browser delivery is an excellent first milestone, while PC and mobile should be treated as their own tested releases, not as automatic consequences of a successful desktop-browser build.
